## Dense Qwen Interpretation

### Base vs Scaled Configuration

| Field | Qwen3 0.6B | Scaled Qwen ~1B | Why it changed |
| --- | ---: | ---: | --- |
| `base_emb_dim` | 1024 | 1280 | Increases hidden-state width and projection sizes |
| `base_num_query_heads` | 16 | 20 | Keeps attention shape aligned with larger hidden size |
| `base_num_kv_heads` | 8 | 10 | Keeps grouped-query attention ratio consistent |
| `base_mlp_dim` | 3072 | 3840 | Scales feed-forward capacity with hidden width |
| `base_num_decoder_layers` | 28 | 32 | Adds depth to reach the requested ~1B target |

### Expected Behavior To Validate Against Logs

- CPU should have the slowest step time because dense transformer training is dominated by matrix multiplication and memory movement.
- GPU should be much faster than CPU because it has high-throughput matrix kernels and memory bandwidth.
- TPU may be competitive or faster depending on compiler behavior, bfloat16 execution, and Colab TPU generation.
- The scaled model should have lower tokens/sec and higher memory use than the 0.6B model.

## DeepSeek MoE Interpretation

### Scale-Down Summary

| Field | DeepSeek2 16B | Assignment MoE | Why it changed |
| --- | ---: | ---: | --- |
| `base_emb_dim` | 2048 | 1024 | Cuts hidden width and projection sizes |
| `base_num_decoder_layers` | 27 | 12 | Reduces depth |
| `num_experts` | 64 | 8 | Major reduction in total MoE parameters |
| `num_experts_per_tok` | 6 | 2 | Reduces active experts per token |
| `shared_experts` | 2 | 1 | Keeps shared expert behavior while reducing total and active parameters |
| `base_moe_mlp_dim` | 1408 | 768 | Reduces each expert's feed-forward size |

### Expected Behavior To Validate Against Logs

- Total parameters are higher than active parameters because only top-k routed experts are used per token.
- MoE may not always be faster than dense at this small scale because routing and dispatch overhead can dominate.
- MoE comparisons should discuss both active compute and total memory footprint.
